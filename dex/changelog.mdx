<Update label="1.19.1" description="2026-11-27">

### Added

- **A unit or a measure's additivity now writes an Elementary column monitor.**
  With `monitors.vendor: elementary`, a column declared `unit: fraction` or
  `unit: percent` gets an `elementary.column_anomalies` under the column with
  the monitors `min` and `max`, which watch it shift inside the bound
  `dex_unit_range` already checks. A column declared `role: measure` gets one
  with the monitors its `additivity` makes meaningful: `sum`, `average` and
  `zero_count` for `additive`, `min`, `max` and `average` for `semi_additive`,
  and `average` for `non_additive`, so `sum` is never written where adding the
  column means nothing. A column both rows reach gets one test whose list is
  the union. Each is written on the model's one time column, carries the
  population's `where_expression`, is reported in `data.monitors` with the
  declaration fields it came from, and names them in `data.decisions`. A
  hand-written `column_anomalies` on the same column and time column is left
  as written, and a column flagged as personal data gets none. ([#1610](https://github.com/exmergo/dex/pull/1610))
- **A declared daily deadline now writes an Elementary `data_freshness_sla`, and
  `maintain verify` judges it.** A time column's `freshness` may state a
  `deadline` (`"07:00"`), its required IANA `timezone`, and optional `days`,
  beside or instead of a `max_lag`; a lag is never read as a deadline. With
  `monitors.vendor: elementary`, the plan writes `elementary.data_freshness_sla`
  with that `timestamp_column`, `sla_time`, `timezone` and `day_of_week`, carrying
  the population's `where_expression`, reported in `data.monitors` and named in
  `data.decisions` by its `freshness.deadline` field (withheld below Elementary
  0.23.1, which first ships it, and where a population value holds a quote on a
  connector that escapes it with a backslash, which the package's own message
  re-escaping breaks). `maintain verify` and `transform build --verify`
  raise `deadline_missed` once the deadline has passed with no value from today,
  by counts alone, with one `data.freshness` record per check. A deadline on a
  `business` basis column is written with a warning: the test needs a value from
  today, which a load of the previous day's events never holds. ([#1611](https://github.com/exmergo/dex/pull/1611))
- **`dex init` proposes the schema the Elementary package writes in production
  for the source allowlist.** Where the package is present or offered,
  `data.elementary.allowlist` says whether the committed allowlist reaches that
  schema, and where it does not, init lists the entry as a non-blocking missing
  input with the `dex config set ... --comment` that adds it. Init never writes
  it: `config set` shows the diff and writes on `--confirm`. A schema the
  connection cannot open yet (the package has not run in production) is reported
  `not_created` and not proposed, since an allowlist entry naming a schema that
  does not exist makes every command refuse. The schema is dbt's
  naming of the package's `+schema` for production, read from `<connector>.prod`
  or the profile output `dbt_prod_target` names, never from the dev namespace;
  where a project's own `generate_schema_name` or a Jinja `+schema` keeps it
  unknown, the missing input says what to commit. A missing input marked
  `blocking: false` no longer makes init an error. `dex config set` gains
  `--comment`, which writes the reason beside the value, and a list it extends
  keeps every line it had, comments included. ([#1618](https://github.com/exmergo/dex/pull/1618))
- **`dex maintain incidents` reads Elementary 0.16.4's tables.** The reader
  records the package's layouts at 0.16.4, the series most installs pin, beside
  0.26.1's, each matched exactly; a 0.16.4 project's failing test is now an
  incident rather than `elementary_release_untested`. Both releases write the
  columns the reader reads alike, so a table upgraded from one to the other reads
  as one history. 0.16.4 records `pass` for any test with zero failures, whatever
  dbt said, so in a run it wrote a pass from a test whose `warn_if` or `error_if`
  can hold at zero failures is read as unobserved, counted under
  `passes_unobserved` with a warning, never as a pass. A column the reader uses
  that a release does not have (0.16.4's `test_result_rows.row_index`) is
  reported unobserved at that release. ([#1619](https://github.com/exmergo/dex/pull/1619))
- **`dex maintain diagnose` checks every cause owner, not only a duplicate
  delivery.** Each open incident now gets an answer for each owner. All are
  judged over the failing test's lineage, at the runs that bound the break:

  - the loader retyping a source column, from the schema axis between the
    bounding snapshot and the warehouse after it;
  - the project changing a model in the commit range, from `maintain verify` on
    the changed model;
  - a package upgrade, from the versions `package-lock.yml` pins at the two
    commits;
  - an edited seed, from the seed file's git hash at the two commits;
  - the schedule building a parent model after its child, from both models'
    build times in Elementary's `dbt_run_results`.

  The build-times read is one bounded statement of ids and times, priced with
  the other checks. A profile of `dbt_run_results` withholds its compiled SQL,
  messages and adapter responses. Where the evidence is missing, a candidate is
  `not_checked` with a reason, such as `unpinned` with no lock committed or
  `no_measured_before` with no snapshot. A `no_cause` answer therefore names
  what it could not rule out.

  ([#1620](https://github.com/exmergo/dex/pull/1620))
- **Dex Telemetry has an overview page.** It covers how `dex init`, your
  declarations, `maintain incidents` and `maintain diagnose` work together to
  monitor a dbt pipeline, and the README has a matching section.

### Fixed

- **The refactor comparison now treats a `profiles.yml` edit as global.** A plan that rewrites a model and also edits `profiles.yml` is compiled through the ancestors of the model on both sides, so a profile edit that moves the dev schema or database no longer makes the two sides resolve `ref()` to different relations without saying so. A plan that only rewrites the model is compared as before. ([#1617](https://github.com/exmergo/dex/pull/1617))
- **Profiling a boolean column on Postgres or Redshift no longer fails the whole
  profile.** Neither warehouse takes `MIN` or `MAX` of a boolean, so the profile
  statement of any table holding one was refused; this stopped the first
  `dex maintain incidents` read of Elementary's tables on Postgres
  (`dbt_invocations.full_refresh`). A boolean column now gets its non-null count
  and no minimum or maximum. ([#1619](https://github.com/exmergo/dex/pull/1619))
- **`dex demo`'s batch loaded twice now holds copies of loaded rows.** The 1,000 extra `order_items` rows repeat the row already loaded with each `order_item_id`, in every column, where before they reused the key with new values. So the repair `maintain diagnose` offers, keeping one row per `order_item_id`, now loses no line item. Every other table, the rows loaded first, and every count the demo quotes (14,000 rows, 13,000 distinct ids, 1,000 rows to remove, 92.9%) are unchanged. Column pairs that held no repeat before, such as `(order_item_id, order_id)`, now repeat with the batch, since every repeated id repeats its whole row. ([#1622](https://github.com/exmergo/dex/pull/1622))

<Update label="1.19.0" description="2026-11-26">

### Added

- **A declared population filter becomes the `where_expression` of the model's Elementary monitors.**
  With `monitors.vendor: elementary`, every monitor a declaration writes now
  carries the model's `population.filters` as its `where_expression`, so the
  monitors measure the rows the model promises and a row outside them bends no
  training history. `includes` is written `<column> in (...)` and `excludes`
  `(<column> not in (...) or <column> is null)`, which keeps the NULL rows an
  `excludes` keeps, unless the column declares `null_rule: never`; several filters
  join with `and`.

  - Each part holding an `or` is parenthesised, because Elementary appends the
    expression to its own time-bucket filter with a bare `and`.
  - Values are literals typed as declared, never cast, with text escaped as the
    `dex_population_filter_literal` macro escapes it on the connector, so write
    them in the column's type. The column is quoted as the adapter quotes it
    where it must be.
  - A filter Dex cannot write withholds the model's monitors
    (`filter_column_not_output`, `filter_unwritable`) rather than writing them
    unfiltered, and a monitor Dex wrote on another population is `stale` and
    kept.

  ([#1571](https://github.com/exmergo/dex/pull/1571))
- **`dex maintain incidents` returns the incidents the run history holds for the selected models' tests.**
  It reads Elementary's tables (`dbt_invocations` and `elementary_test_results`)
  where the package is installed and uploading, and dbt's `run_results.json`, and
  folds both through the one incident lifecycle rule. Elementary is read over the
  newest 20 invocations by default (`--invocations <n>`, up to 2000): a run count,
  so the price does not depend on the schedule. Every statement goes through the
  query firewall and the source allowlist, and the whole read is priced before
  anything runs, so on a billed connector the first call answers
  `needs_confirmation` having sent no statement. `data.sources` reports each source as
  `read`, `missing` or `refused` with a reason code. A schema outside the
  committed allowlist is refused before any connection opens, with the
  `dex config set` that adds it. With no package, the next steps name the install
  `dex init` offers. `data.window` names the invocations read, `data.price` the
  estimate and what it settled at, and each incident carries its coverage and
  retention bound. `DexEngine.incidents()` returns the same result. ([#1572](https://github.com/exmergo/dex/pull/1572))
- **`explore semantic query|values` on a Cube layer now runs `--local` on ClickHouse and Trino.**
  Cube renders the SQL and Dex executes it through its own connector, under the PII gate and the cost guard, as on DuckDB, Postgres, BigQuery, Snowflake and Redshift.
  Both dialects are held to a recorded golden of what Cube Core v1.8.14 renders.
  The statement runs in a UTC session on both, so a timestamp with no zone means what Cube means whatever the machine's or the server's time zone.
  A rolling window is the exception on ClickHouse: Cube renders a join on inequalities alone, which ClickHouse 25.3 refuses.
  Databricks is still refused by name on `--local`. ([#1573](https://github.com/exmergo/dex/pull/1573))
- **`dex maintain diagnose` takes each open test incident to a cause, or says no cause was confirmed.**
  It reads the incidents as `dex maintain incidents` does and bisects each one
  over its coverage timeline: after the last observed-good run, through the first
  observed-bad one, where a run that recorded nothing widens the range and never
  narrows it. The committed `maintain snapshot` series (the versions of
  `.dex/snapshot.json` in the repository's history) bounds the break where there
  is one; on a project's first day there is none, and the answer names the window
  no recorded state of the warehouse covers. Each candidate cause is confirmed or
  ruled out by a check Dex already has, named in the answer. This release checks
  a uniqueness test failing because the loader delivered a key twice, with the
  grain axis of `dex maintain check` on each source the tested model reads. With
  no confirmed cause the answer lists what was ruled out and the unseen window,
  and never names the likeliest candidate. A confirmed cause's repair is handed
  to `transform` as a next step, never written. `DexEngine.diagnose()` returns the
  same result. ([#1574](https://github.com/exmergo/dex/pull/1574))
- **A plan tags the columns Dex marks as personal data so Elementary keeps no sample of them.**
  With `monitors.vendor: elementary` and the package installed, each column a
  written model's YAML marks as PII, at any confidence, gets Elementary's tag in
  `config.meta.tags`, the model gets it in `config.tags`, and the plan adds
  `disable_samples_on_pii_tags: true` under `vars:` in `dbt_project.yml`. The
  project's own tests, not only Dex's, then keep no sample of those columns in
  `test_result_rows`.

  - The tag is `pii`, or the first entry of the project's own `pii_tags`.
  - A plan that rewrites an existing model's SQL gets the tags without the
    switch, which `transform declare` then adds in a plan of its own, so the
    rewrite keeps its refactor comparison and downstream impact check.
  - A warning states the trade: every test on a tagged model, the project's own
    included, keeps no sample of its failing rows.
  - `data.pii_tags.rule` says what the installed release does with the tags:
    nothing before 0.19.2, the model tag only from 0.19.2 to 0.19.4, both from
    0.20.0.
  - A `false` a person wrote under a PII flag is never tagged, and a
    `disable_samples_on_pii_tags` the project sets is kept as written.
  - `transform declare` proposes a model whose marks predate the tag.

  ([#1576](https://github.com/exmergo/dex/pull/1576))
- **`dex demo` now shows an incident and its cause, offline.** Beside the warehouse
  and its config, the demo writes a small dbt project under `demo_project/dbt/`: a source
  over `orders` and `order_items`, a staging model over each, and a `unique` and a
  `not_null` test on each key. Its `target/` holds the artifacts of a seeded
  `dbt build` in which `unique_stg_order_items_order_item_id` failed, because of
  the batch the demo loads twice.

  - `dex maintain incidents` then returns that incident, open, with no build
    first.
  - `dex maintain diagnose` names the loader's duplicate delivery of
    `order_item_id` as the cause, measured on the source the model reads.
  - The printed next steps end with both commands.
  - The demo still runs no dbt, installs no package and opens no network
    connection; the artifacts are generated and pinned by a digest.
  - The project sits one level down, so `analytics/`, the directory the docs give
    your own project, stays free and `dex transform init analytics` still works
    after the demo. An existing `demo_project/` beside the target is refused
    before anything is written. Under an existing `.dex/config.yml` no project is
    written, as no config is.
  - Once the warehouse is written, a config or project write that fails or is
    interrupted part way removes the project, the config and the warehouse it
    made, and nothing it did not make: a config another `dex demo` wrote in the
    same directory meanwhile is refused, never replaced. A failure while the
    warehouse itself is loading removes it, as before; an interrupt there can
    still leave it.

  ([#1587](https://github.com/exmergo/dex/pull/1587))
- **`dex demo` now shows the incident from Elementary's tables, with when it began.**
  The demo seeds the history of seven weekly builds of its dbt project.

  - **Elementary's tables**, in `main_elementary`: `dbt_invocations` and
    `elementary_test_results`, built from the reader's recorded 0.26.1 layout, and
    the layout's two other tables, empty. One week the package's hooks were off,
    and it holds no row.
  - **The package**, declared at 0.26.1 in `packages.yml`, with that release
    recorded where the resolver reads it.

  `unique_stg_order_items_order_item_id` passes in four builds and fails in the last
  two, because of the batch the demo loads twice. So `dex maintain incidents`
  returns the incident from the `elementary` source, with the build it was first
  observed in, and the week with the hooks off read as a missed run inside its
  onset. `dex maintain diagnose` names the loader's duplicate delivery over that
  break.

  - The builds are dated back from when `dex demo` ran, so the incident stays open
    for about three weeks. The project's source files are dated a day before the
    oldest build, so they move too. Every other date in the demo is still fixed.
  - `explore map` leaves the package's tables out of the ranking, so the tour's
    counts are unchanged.
  - The demo still runs no dbt, installs no package and opens no network
    connection. To build its project, run `dex transform deps` first: the build
    reads the recorded release as an installed package and would not install it.

  ([#1588](https://github.com/exmergo/dex/pull/1588))
- **`maintain diagnose` names who reads what broke.** Each diagnosis carries
  `semantic_readers`: the semantic models on the failing test's model whose
  entities, dimensions and measures read its columns, and the metrics built on
  those measures, read from dbt's semantic layer with no warehouse query. A
  semantic model on a model built from the tested one is not followed, and each
  read says so. A member whose expression is computed is listed as `unresolved`
  rather than guessed, and so is a member reading a versioned model's column,
  since the fingerprint records a `ref()` by name and not by version. A project with no semantic layer reads `absent`, not
  an empty list. ([#1598](https://github.com/exmergo/dex/pull/1598))
- **`dex demo` writes a semantic layer that reads its failing column.** The demo's
  dbt project gains `models/semantic/`: the time spine dbt requires, an `orders`
  semantic model with the metrics `orders`, `revenue` and `average_order_value`,
  and an `order_items` semantic model whose primary entity is `order_item_id`,
  the column the seeded test fails on. `maintain diagnose` names that entity
  beside the cause, and the seeded `target/semantic_manifest.json` lets
  `explore semantic list --local` read the layer with no `dbt parse` first. ([#1600](https://github.com/exmergo/dex/pull/1600))
- **A small-domain dimension column writes an Elementary `dimension_anomalies`.**
  With `monitors.vendor: elementary`, a column declared `role: dimension` whose
  cached domain is at most 20 distinct values gets its own
  `elementary.dimension_anomalies` (`dimensions: [<column>]`) on the model's one
  time column, carrying the population's `where_expression`. Each column gets its
  own test, because the package groups a `dimensions` list by the columns'
  combination. The domain is read from the exploration cache, never measured. A
  column over the bound is `domain_too_large`. A column with no cached count is
  `not_profiled`, and a warning names the `explore profile` that would supply
  one. A column Dex flags as personal data is `pii_flagged` at any size. A
  monitor Dex wrote on a column that no longer qualifies is reported `stale` and
  kept. `transform declare` now also returns `data.monitors`. ([#1609](https://github.com/exmergo/dex/pull/1609))

### Changed

- **Dex spells each connector's dev target as `dev`, beside `prod`, keeping the previous keys as aliases.**
  Connector configuration now unifies the dev target namespace under the canonical `dev` key across all connectors, matching `prod`:

  - DuckDB: `duckdb.dev` (database name)
  - BigQuery: `bigquery.dev` (dataset or project.dataset)
  - Snowflake: `snowflake.dev` (database.schema)
  - Databricks: `databricks.dev` (catalog.schema)
  - PostgreSQL: `postgres.dev` (schema)
  - Redshift: `redshift.dev` (schema)
  - ClickHouse: `clickhouse.dev` (database)
  - Trino: `trino.dev` (catalog.schema)

  The connector-specific keys (`dev_dataset`, `dev_database`, `dev_schema`, `dev_catalog`) remain supported as backward-compatible aliases. Existing configuration files validate without warnings and produce identical runtime behavior. New projects initialized with `transform init` render `dev`, while existing files retain their written spelling.

  ([#1541](https://github.com/exmergo/dex/pull/1541))
- **The agent procedure sends an agent to `dex maintain incidents` first when a test fails or a model is wrong.**
  Step 6, **Maintain**, now opens with that routing: `dex maintain incidents` first, then `dex maintain diagnose` for an open incident's cause and `dex maintain verify` on the models whose tests they name. It also says what an empty answer means: where `data.sources` reports Elementary `missing` or `refused`, the run history was not read, which is not a clean history; the source's `reason_code` says why, and for a project without the package `data.next_steps` names the install `dex init` offers, which starts it. The `maintain` skill now triggers on "when did this test start failing" and "what changed when it broke".

  `dex procedure` returns the new text and a new `digest`, so a copy pasted into a repository's own `CLAUDE.md` or `AGENTS.md` now reads `stale` under `dex procedure --check`, which exits as an error. Refresh it with `dex procedure --block`. ([#1597](https://github.com/exmergo/dex/pull/1597))

### Fixed

- **A mart whose grain is a single time column now derives a semantic model dbt parses.** The primary entity took the column's name, the same as the time dimension, so dbt rejected the model in any project that defines a metric. The entity is now named `<stem>_<column>` with `expr: <column>`, where the stem is the model name without its layer prefix (`fct_`, `fact_`, `dim_`, `mart_` or `marts_`), so `fct_daily` with grain `output_day` gets `daily_output_day`. It is chosen before the foreign keys so one that joins by the column's old name still joins. A plan settles every mart's primary entity name in a first pass, then drafts the foreign entities that join an existing entity or a settled primary until the drafts settle, and resolves every foreign key in the plan against those drafts and the layer as it stands. A mart therefore joins the same name whatever order the plan derives them in, including marts that reference each other and a reference to a parent column that is itself a foreign key. A foreign key that cannot join what it references (the plan derives that column with no entity, or its entity is one this model already uses) is not derived, and says so, rather than offered under a name that joins nothing. A dimension of the child that already has the parent's entity name is renamed `<stem>_<name>` with `expr: <name>` so the join name stays. Each replacement name, and a foreign key's fallback name, is numbered when the model's own elements, the entities its foreign keys join by, an entity name the layer or plan already uses, or another element type anywhere in the semantic layer or in another mart of the same plan already hold it. ([#1439](https://github.com/exmergo/dex/pull/1439))
- **Stored plan IDs scope to the dbt project.** When multiple dbt projects share
  a repository and plan store, identical edits and intent generated colliding plan
  IDs, causing the second plan to overwrite the first plan's recorded project
  directory. `_plan_id` now incorporates normalized relative project paths,
  ensuring stable, portable identities across checkouts and operating systems
  while existing stored plans remain retrievable and applicable by ID. ([#1547](https://github.com/exmergo/dex/pull/1547))
- **`maintain incidents` no longer says no failure has a known start when
  Elementary dates it.** When dbt's `run_results.json` has a place in
  Elementary's order, as an invocation Elementary also recorded
  (`placed: in_window`) or one that started after Elementary's newest run
  (`placed: after_window`), the run-results note saying no failure has a known
  start is left out, since a failure Elementary saw pass before that run is
  dated. Where the run itself opened incidents with no known start (a test
  Elementary holds no result for), a note in the same place counts those
  incidents alone, so it holds beside an incident that is dated. A run read
  alone, or with no place in Elementary's order, keeps the note as before. ([#1593](https://github.com/exmergo/dex/pull/1593))

<Update label="1.18.5" description="2026-11-23">

### Added

- **Test failures fold into incidents by one rule, whatever their source.**
  `exmergo_dex_core.maintain.incidents` adds an `Incident` value type and
  `fold_incidents`, which turns the outcomes every test-result source records into
  incidents: an observed failure opens or extends one, two consecutive passes from
  the source that opened it close it (set per check), an unobserved run neither
  opens nor closes one, a check that stopped running ends `no_longer_observed`
  against a schedule derived from its history, and a source that disagrees is
  attached as evidence. A first failure no source holds a pass before is reported
  `unknown`. Incidents carry ids, statuses and times, never a value from the data.
  The command that returns them comes in a later release. ([#1556](https://github.com/exmergo/dex/pull/1556))
- **A coverage timeline that never reads an unobserved interval as good.**
  `exmergo_dex_core.maintain.timeline` lays one source's runs out in invocation
  order on a named heartbeat (`dbt_invocations`, else the orchestrator's run
  history, else the `maintain snapshot` series, and it says which and why), and
  marks every interval that recorded no outcome as unobserved with its reason: a
  gap longer than the expected schedule allows, a run with Elementary's hooks or
  test uploads off, a missed snapshot, the time before retention, or a run that
  did not check the test. Each run carries its commit, or `unknown`. Per test, the
  history gives the last verified run and each break, after the last observed
  pass up to and including the first observed failure, widened by any unobserved
  interval between them. Incidents now carry their coverage on that timeline and
  their `onset` break. ([#1561](https://github.com/exmergo/dex/pull/1561))
- **The Elementary reader holds the package's tables to a recorded layout, and refuses one it does not know.**
  Dex reads `elementary_test_results`, `dbt_invocations`, `test_result_rows` and
  `data_monitoring_metrics` as evidence, and their columns can change between
  releases without the package calling it a breaking change.
  `exmergo_dex_core.maintain.elementary_layouts` records each table's columns at
  Elementary 0.26.1, copied from the package's model files at that tag, and
  checks the warehouse's catalog before a read touches the tables:

  - A release with no recorded layout is refused with `elementary_release_untested`
    (or `elementary_release_unknown` where none can be read), before the catalog
    is asked. The reader's releases are held to the ones the Elementary fixture
    runs, so they can be fewer and never more.
  - A column the reader uses that is gone is `elementary_column_missing`, one in
    another type family is `elementary_column_retyped`, and a table the catalog
    lists nothing for is `elementary_table_missing`, each naming the table and the
    column. A catalog listing past 500 columns is refused as
    `elementary_catalog_too_large`.

  The refusal is `ElementaryLayoutError`, importable from `exmergo_dex_core`. No
  command reads the tables yet: the incident reader (#1471) and
  `dex maintain incidents` (#1472) build on this check.

  ([#1562](https://github.com/exmergo/dex/pull/1562))
- **The engine reads test outcomes from Elementary's tables as incident observations.**
  `exmergo_dex_core.maintain.elementary_incidents` reads `dbt_invocations` and
  `elementary_test_results` in the schema the package writes, and returns the
  observations and run history `fold_incidents` and `build_timeline` take. It
  selects ids, status and severity tokens, an anomaly test's column and metric,
  each run's times, commit and package version, and counts. It never selects a
  sampled row or a value a test failed on.

  - `plan_read` holds both tables to the release's recorded layout before writing
    a statement, and refuses where the layout check refuses.
  - `read_elementary` sends every statement through the query firewall, the
    source allowlist, the cost handshake and the query ledger, as `explore query`
    does. The first read on a fresh cache profiles the two tables and reports
    `first_read` with what the profiling was priced at.
  - One call reads at most 2,000 invocations and 100,000 result rows. It counts
    first and refuses past either bound (`elementary_read_too_large`) before it
    reads a row. `since` reads a later window.
  - Result rows are deduplicated on `id`, and each run gets one place in the
    order, by `run_started_at` and never by `created_at` alone. A result whose
    run has no `dbt_invocations` row is counted and not observed.
  - It refuses, each with its own code: an empty history, an invocation with no
    readable start, an invocation written twice with different starts, a run
    written by a release other than the one checked, a status it does not map,
    one result id holding two records, and an id too long to hold.

  The refusal is `ElementaryReadError`, importable from `exmergo_dex_core` with no

### Fixed

- **A Metric View `date` format without `date_format`, or a `date_time` format
  without both `date_format` and `time_format`, is refused.** Databricks refuses
  both on `CREATE VIEW ... WITH METRICS`; dex read them as valid temporal fields.
  **A derived semantic definition is placed by the siblings the same plan
  creates.** `transform plan` now counts a model the plan itself writes when it
  looks for the catalog and schema a native layer's views already read, so a mart
  planned beside its staging model is no longer placed on a bare table name. ([#1258](https://github.com/exmergo/dex/pull/1258))
- **A deployed Databricks Metric View no longer breaks `maintain check` or a
  profile.** The Databricks connector inventoried a Metric View in the source scope
  as a relation, and Databricks refuses a plain `SELECT` of its measure columns
  (`METRIC_VIEW_MISSING_MEASURE_FUNCTION`), so the grain axis failed the whole
  command. Unity Catalog objects of type `METRIC_VIEW` are now left out of the
  inventory; their YAML is read from the repository under
  `semantic.vendor: databricks`. `maintain reconcile` in a repository whose only
  layer is a semantic one no longer refuses when none of its findings is a schema
  one: they are advisory. A plan's notes are no longer repeated in reconcile's
  warnings. ([#1259](https://github.com/exmergo/dex/pull/1259))
- **Moving an unchanged aggregate into a CTE is no longer an aggregate change.** In `data.change_scope`, `transform plan` compared each output column's aggregates as written, so extracting `count(*) as part_count` into a grouped CTE and reading `p.part_count` in the final select reported an undeclared `aggregate_changed` ("aggregates nothing"). The comparison now follows the column through the top-level CTEs it reads. When the rows reaching the aggregate are produced alike on both sides (the same filters, the same grouping and `HAVING` where the aggregate is computed and elsewhere, the same row `DISTINCT` columns and join conditions, each column compared as the table it reads, the same tables read as often, and no outer join, `LIMIT`, sample, window function, `QUALIFY` or derived table on the way), an aggregate that only moved is listed as `expression_changed` ("reads the same calculation through a CTE"), which needs no decision. A changed aggregate, a new cast or new NULL handling is still flagged, also when it was added inside the CTE, and any other move, or a column that cannot be traced, is compared as written. An output whose text is unchanged but that now reads a differently named CTE is compared through it too, so a calculation changed there is reported. The moved query's grouping and join changes are still reported under population. (#1253) ([#1264](https://github.com/exmergo/dex/pull/1264))
- **A semantic file that does not parse is named instead of hiding its definitions.** The semantic verbs read every project YAML file for the definitions it declares, and one that failed to parse was skipped silently: a metric living in it read as "not in the project" and a definition edit with no `path` was told to "give it a path", sending the caller looking for a missing definition or writing a duplicate when the real problem was a syntax error. The read now reports each skipped file and why, and a refusal that would claim a name is absent names the files it could not read: "`models/semantic.yml` could not be read (does not parse as YAML at line 44), so definitions in it are not visible". (#1268) ([#1277](https://github.com/exmergo/dex/pull/1277))
- **Reconcile finds the declaration of a mart that lost its key.** After `maintain check` reported `key_lost_uniqueness` on a mart such as `dim_customers`, `maintain reconcile` looked for `models/staging/stg_dim_customers.yml`, found nothing, and only advised adding a `unique` test by hand. It now resolves the model the project builds as that relation, wherever it lives, and proposes the `unique` test in the YAML that declares it. When the key already has a `unique` test, the proposal now says so: that this test fails on the duplicates (unless they are NULL keys, which dbt's `unique` ignores) when the finding is on the model's own relation and the test is a plain `unique`, and otherwise that it is already declared. A relation the project also declares as a source table keeps the staging convention. ([#1278](https://github.com/exmergo/dex/pull/1278))
