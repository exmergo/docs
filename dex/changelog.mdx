<Update label="1.18.0" description="2026-11-16">

### Added

- **`maintain verify` judges a project format's declared foreign keys without dbt
  artifacts.** A project format other than dbt (one named under `project.format`)
  can declare foreign keys, but nothing measured them: verify suppressed the join
  contract and parent population for want of a dbt `target/`, and dbt's own
  `relationships` test result was the only judge. Each declared foreign key is now
  measured against its parent with the join contract's coverage probe, placed
  where the format's `model_relations` puts each side, and reported as one record
  per key under `data.foreign_key_coverage` (`model`, `column`, `to_model`,
  `to_column`, and a `status` of `satisfied`, `contradicted`, `not_applicable` or
  `unchecked` with a `reason_code`). Any non-NULL child value the parent lacks is a
  high `foreign_key_orphans` finding, since a foreign key states containment. A
  model the format places in no relation is `unchecked` with
  `no_declared_relation`, never found by name. On a metered connector the probe is
  priced in verify's one offer. A dbt project is unchanged: dbt still judges these
  through its own `relationships` tests. ([#1217](https://github.com/exmergo/dex/pull/1217))
- **`dex maintain coverage` inventories the tests a dbt project declares.** It
  reads a fresh `dbt parse` of a copy of the project, so it is free on every
  connector, opens no connection and needs no baseline. For each enabled model,
  source, snapshot and seed it counts its own generic, singular, unit and
  freshness tests (with each test's severity), lists the tests on downstream
  resources apart, says whether an incremental model has a unit test that takes
  its `is_incremental()` branch, and splits documented columns into asserted and
  unasserted. Every ratio in `data.summary` names its numerator, denominator and
  what the denominator counts; package and disabled resources are counted and
  named under `excluded`. It takes the `maintain verify` selector and `--full`,
  reports only (never fails on low coverage), and is reviewed for values-free
  mode. `DexEngine.coverage()` is the library spelling. ([#1328](https://github.com/exmergo/dex/pull/1328))
- `transform build --verify --for-plan` now measures what a plan did to the models below its edits (#1231). The models the plan rewrote and every unedited model below them are re-executed against the tree before the plan, which `transform apply` now records on the plan as `baseline_sources` (else the git `HEAD` blob whose hash the plan recorded). Per model, `data.verification.impact` counts rows and keys on each side (kept, removed, added, duplicated; keys compared as text, so a retyped key still matches) and, on a mart, the kept keys each column changed on; counts and names only. An unedited model whose rows or keys moved is a `downstream_population_changed` finding naming the edit upstream, attributed `introduced`, and an `unverified` reason that keeps the build from reading `validated`, unless its declaration records the population as an assumption at `request` or `contract` tier. `data.completion.impact` leads with the largest changes. On billed connectors the statements are priced with the build as `(downstream impact)`, and a model above a quarter of the command ceiling is `unchecked: cost`. `data.change_scope.downstream` names, at plan time and for free, the unedited models below each rewrite. ([#1333](https://github.com/exmergo/dex/pull/1333))
- **`dex maintain coverage` reports last-run status, recorded mutation strength
  and declared-fact coverage beside the test inventory.** Each test carries its
  status in the newest `run_results.json` a dbt build wrote (Dex's or a plain
  `dbt build`'s), `not_run` where that run did not include it, with the run's
  invocation and age. `transform test --mutate` now records each model's result
  in `.dex/`, and coverage reads it back as the model's `strength`: `fresh`,
  `stale` (naming whether the model's SQL, its tests or a downstream test it ran
  changed), `missing` or `untestable`, counted per status with score bands and
  no project score. A `declarations` section names, for each declared fact, the
  dbt tests and `maintain verify` checks that can judge it, or that nothing does.
  All of it is free and connectionless. Store backends gain an optional
  `MutationRecords` capability, held to the conformance suite as
  `MutationRecordsContract`. ([#1343](https://github.com/exmergo/dex/pull/1343))
- **`maintain coverage --mutate` refreshes stale and missing mutation scores, and coverage lists the columns singular tests read.** `--mutate` runs `transform test --mutate` for each model whose recorded score is `stale` or `missing`, in selector order (else missing first, upstream first), at most 25 per run (`--max-models` narrows), and reports what it did under `data.refresh`. On a metered connector the whole batch is priced and confirmed once, each run draws on what the budget has left, and the models it did not reach are `not_run`; it is free on DuckDB, dev target only, and refused in values-free mode. Without `--mutate` the command still opens no connection. A model with no SQL to plant a defect in is now recorded and reads `untestable` until it changes, so a refresh always moves on. Each resource's `columns.referenced_columns` lists the columns its singular tests read, with the role each is read in (`predicate`, `join`, `aggregation`, `grouping`, `projection`), counted apart as `columns_referenced_only` and never as asserted; `data.singular_tests` names every test that could not be read, with a reason code. ([#1349](https://github.com/exmergo/dex/pull/1349))
- **Governed `explore semantic query` and `values` on Snowflake Semantic Views, and `explore semantic list --deployed`.** Under `semantic.vendor: snowflake`, Dex renders `SELECT * FROM SEMANTIC_VIEW(<deployed view> DIMENSIONS ... METRICS ... [WHERE ...])` from the repository's catalog and runs it through its own Snowflake connector under the cost guard (`execution: dex`); every other connector is refused by name. Tokens are the catalog's (`sales.orders.revenue`, `sales.revenue_per_customer`), one view per query, and result columns carry them. A grain-suffixed time dimension (`sales.orders.order_date__month`) renders as `DATE_TRUNC`, `--where` is a Snowflake predicate over dimensions and facts, and a query of facts alone takes `--group-by <fact>` and no metric. Refused by name before anything is sent: facts beside metrics or dimensions, a private, window, level-of-detail or `using_relationships` member, a view declaring `variables`, a dimension the metric's table does not reach many-to-one, a grain on a categorical dimension, a bare `--grain`, and a `--where` naming a metric or one Dex cannot read. The PII gate screens grouped and filtered members and the inputs of a metric that returns one of its values, through the catalog's lineage. Before the cost handshake, Dex locates the deployed view with a warehouse-free `SHOW SEMANTIC VIEWS` over the source allowlist, reads it back with `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` (which resumes no warehouse), and refuses the query when anything it relies on differs from the repository's file, naming the member and the field; a view defined only in the repository, or in two allowlisted schemas, is refused by name. The statement is priced from the base tables the members reach, since Snowflake keeps no bytes for a semantic view. `explore semantic list --deployed` reads the deployed views instead of the files, with `source: deployed` and per-view `coverage` (`full`, `limited`, `refused`); a plain `list` never contacts Snowflake. ([#1355](https://github.com/exmergo/dex/pull/1355))
- **A live integration suite for Snowflake Semantic Views, and the CI role it deploys with.** `tests/integration/test_snowflake_semantic_views.py` deploys two corpus views over the TPC-H sample data into a scratch schema and holds Dex to them: the read-back comparing clean, `list --deployed`, five governed queries and values against SQL written by hand over the base tables, the stale-definition refusal, and the `maintain` drift loop through `reconcile` and `apply`. `scripts/setup_snowflake_ci.sh` provisions `DEX_CI_SV_DEPLOYER`, the role the suite deploys with, kept apart from the role Dex runs as, and `scripts/setup_snowflake_semantic_views.sh` grants the read role OPERATE on its warehouse so `snowflake.suspend_after_command` works. The docs now state plainly what the Snowflake Semantic View vendor does not do in this release. ([#1356](https://github.com/exmergo/dex/pull/1356))
- **`maintain coverage` lists a native semantic layer's declarations.** Under `semantic.vendor` set to Ossie, SLayer, Cube, Databricks or Snowflake, the declarations section adds the layer's own facts beside the dbt manifest's, and every record names its `source`. The keys and joins the layer declares are the ones `maintain grain` re-verifies, so they read `dex_verify` with `declared_grain_not_unique`, `declared_join_orphans` and, for a join declared `many_to_one` or `one_to_one`, `join_cardinality_exceeded`. What the layer's `dex` metadata states (roles, references, population, unit, additivity) reads `none`, since nothing checks it on that layer. A fact a dbt model and the layer both declare on the same relation, spelled alike, is listed once per source with `also_declared_by` and counted once. Still free and connectionless, and no population value or rule text is shown. ([#1358](https://github.com/exmergo/dex/pull/1358))
- **Snowflake Semantic Views read from the account alone: `semantic.deployment: snowflake_account`.** Under `semantic.vendor: snowflake`, the new deployment reads the catalog from every semantic view in the source allowlist's scopes, with no repository file needed: a warehouse-free `SHOW SEMANTIC VIEWS` per scope, then `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` per view, each read-back checked by the same validator that reads a file. It is the Snowflake counterpart of `dbt_cloud` and, like it, is read only by `explore semantic list|values|query` and by `explore relationships|map --use-hosted-semantic-layer`, which now fold in the account's keys and joins on their base tables. Dex still renders `SEMANTIC_VIEW(...)` and runs it through its own Snowflake connector (`execution: dex`), so the cost guard, the source allowlist and the PII gate apply exactly as under `local`. What changes is trust. The deployed definition is the only one, so nothing is checked against a file, and every result says so: `list` carries `source: account`, `query` and `values` carry `definition_source: account`, and each carries a warning. `coverage` names every view: `full`; `limited`, where a read-back reads a member it does not carry; or `refused`, for a read-back that was refused or failed validation, or for a name held in two allowlisted scopes, with both copies named and `--scope` suggested. The deployment is opt-in only and never a fallback when `semantic.snowflake.files` is empty. Configured files stay optional and keep serving `maintain`, `transform`, `--use-project` and `--local`, which checks the deployment against them. A deployed view that a configured file describes is named on its result (`repository_file`), takes the file's spelling, and is never silently passed over. ([#1360](https://github.com/exmergo/dex/pull/1360))

### Changed

- **A build says what the plan introduced, and an unfinished change no longer reads as validated.**
  A `transform build --verify --for-plan` now classifies each finding as
  `introduced`, `unattributed` or `existing`, judged against the last `--verify`
  build recorded before the plan was applied and against the manifest's lineage,
  and lists the introduced ones first, in `data.verification.introduced` and at the
  head of `data.completion.verification`, so a new high-severity finding is never
  cut or buried below inherited ones. Where every deliverable built but part of the
  change is still open (a rewrite applied uncompared while its baseline was ready,
  an undeclared population change, or an introduced high-severity finding),
  `data.outcome` reads `built_unverified` with each reason under
  `data.completion.unverified`; `data.evidence.outcome` keeps `validated`.
  `transform apply` now refuses a plan whose change scope records an undeclared
  population change, naming each under `data.undeclared_population_changes`, until
  an assumption records it or `--accept-population-change "<reason>"` accepts it,
  which is recorded on the plan. ([#1329](https://github.com/exmergo/dex/pull/1329))
- **The skills stay on a supported Python when your newest is 3.15.** Dex supports
  Python 3.11 to 3.14. The skill wrappers now hold both their own interpreter and
  the engine's environment to that range, so uv picks an installed 3.14 or older,
  or downloads one, instead of installing the engine on 3.15, where dependencies
  that ship no 3.15 wheels fail to build (the Databricks extra did). An explicit
  `UV_PYTHON` still wins. The README, the installation page and the package README
  state the range, and the installation page shows `uv tool install --python 3.14`
  for a standalone install on a machine whose newest Python is 3.15. ([#1335](https://github.com/exmergo/dex/pull/1335))
- **Query results now serialize list and array cells as JSON arrays instead of Python repr strings.** Cells with array types previously fell back to string coercion in `json_safe`, emitting Python repr strings like `"[1, 2]"`. Array cells now serialize as JSON arrays, with nested cell-width truncation applied to long string elements and payload-byte caps preserved. ([#1337](https://github.com/exmergo/dex/pull/1337))

### Fixed

- **Qualifying a GROUP BY key is no longer reported as a grain change.**
  Table qualifiers on GROUP BY keys are stripped during comparison so alias-only
  refactors do not trigger `group_by_changed` and keep the population classified
  as kept. Real grain changes, including case changes in quoted identifiers and
  string literals, continue to be reported. ([#1174](https://github.com/exmergo/dex/pull/1174))
- **Honor runtime error and partial success dbt statuses in standalone maintain verify.** The standalone build status sweep now reuses shared build status classification, reporting `runtime error` and `failed` as `node_failed` findings, tracing skipped descendants back to their failed ancestors, and noting unrecognized statuses like `partial success` and `no-op` as unchecked rather than omitting them. ([#1338](https://github.com/exmergo/dex/pull/1338))
- **Establish build completion and coverage for plans that only add dbt tests.** `required_nodes` now resolves singular test edits (`EditKind.TEST_SQL`) and native unit test definitions (`unit_tests:` in schema YAML) to their expected test nodes, including across configured test paths. Build completion recognizes passing and warning test runs as satisfied test deliverables without conflating test execution with model rebuilds. Skipped, disabled, failed, or missing tests are reported explicitly and prevent validated completion, while unrelated model builds report `unrelated` outcome. ([#1340](https://github.com/exmergo/dex/pull/1340))
- **SLayer authoring and retype checks resolve measure references read through joins.** Saved measures that aggregate a column across single-hop or multi-hop joins now evaluate that column's allowed aggregation rules, including primary key restrictions and type defaults for ARRAY and TEXT columns. When a joined column is retyped, maintain schema lists affected dependent measures under `breaks_measures` and advises on the required measure rewrites. Unknown or unresolvable joins remain explicitly unchecked during authoring validation. ([#1344](https://github.com/exmergo/dex/pull/1344))
- **Reconcile links covered advisories to the native semantic plan.**
  When a mechanical semantic plan is validated during reconcile, advisories that
  the plan already repairs are linked to it instead of being repeated as
  independent manual proposals. Uncovered advisories, such as removals held back
  by guards or unrepresentable repairs, remain separate manual proposals. ([#1345](https://github.com/exmergo/dex/pull/1345))
- **A nation, country, region or continent name is no longer flagged as a personal name.** The generic `*_name` PII match now treats `nation`, `country`, `region` and `continent` as non-person qualifiers, so `nation_name` can be grouped by in a governed semantic query instead of being refused as PII. A bare `name`, a `customer_name`, an ambiguous `n_name` and a `city_name` (address data) are still flagged. ([#1356](https://github.com/exmergo/dex/pull/1356))
- **Ossie snapshots record which key is the primary key and which are `unique_keys`.** A violated or lapsed `unique_keys` entry was worded as a primary-key claim, in the finding and in the `maintain reconcile` advice. The snapshot now records `key_claims` for each Ossie key, so both say the layer declares the columns unique. A key left out because a field links no column drops its claim too. Snapshots taken before this read as they did.

<Update label="1.17.9" description="2026-11-13">

### Added

- **`semantic derivation` normalizes double underscores in derived semantic model names.**
  Marts following Fivetran naming conventions (such as `intercom__threads`) derive
  valid MetricFlow semantic model names (`intercom_threads`) while preserving the
  underlying `ref('intercom__threads')` reference. ([#1214](https://github.com/exmergo/dex/pull/1214))
- **Ambiguous `ref()` inputs resolve through compiled dbt manifest.** When an input matches multiple cached relations (such as legacy and dev builds), `transform plan` and `transform declare` resolve it against the compiled manifest's relation for target when fresh and matching. ([#1242](https://github.com/exmergo/dex/pull/1242))
- **`semantic.vendor: snowflake` reads Snowflake Semantic View files as the
  semantic layer.** Name the Semantic View YAML files in
  `semantic.snowflake.files` (the form `SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML` takes
  and `SYSTEM$READ_YAML_FROM_SEMANTIC_VIEW` returns) and `explore semantic list`
  (with `--metric`, `--for-dimension` and `--search`, which also matches
  synonyms) answers from them. The files are read statically with no Snowflake
  connection, and validated by dex's own port of Snowflake's specification and
  validation rules, qualified against `verify_only` on a live account. Every
  refusal names the file and the element, and a `.sql` file and a legacy Cortex
  Analyst model are refused by name.

  Every name carries its view:
  - logical tables are semantic models `view.table`;
  - dimensions, time dimensions and facts are `view.table.member`, with facts
    marked never groupable;
  - a metric that is one aggregate is a measure and a simple metric, and one
    metric over another is a ratio.

  Primary keys are entities, and every primary and unique key and every
  relationship (with its arity) reach
  `explore relationships|map|profile --use-project` at confidence 1.0.
  `maintain snapshot` fingerprints the layer so
  that a view read back from Snowflake matches its file, and `maintain grain`
  measures the keys and arities. Sample values are never surfaced. Governed `query`
  and `values` are not available yet and refuse by name. Install with
  `exmergo-dex-core[semantic-views]`.

  A deployed semantic view is never inventoried or probed: `SHOW VIEWS` does not
  list one, and the inventory skips its members in `SHOW COLUMNS`. The dev-namespace
  check still counts it as content.

  ([#1313](https://github.com/exmergo/dex/pull/1313))
- **`semantic snowflake define|update|plan` authors Snowflake Semantic View files,
  and a declared mart derives a logical table.** Whole files listed in
  `semantic.snowflake.files` are validated together with dex's port of Snowflake's
  rules and stored as a reviewable plan that `transform apply` writes byte for
  byte, keeping each file's mode. A path off the list, a `.sql` file, another
  suffix and a delete are refused by name, the first with the `dex config set`
  that adopts it. Every error anywhere in the set refuses the plan. In a file the
  plan writes, an unknown key, `access_modifier` on a dimension, and a read
  qualified with its own table that names no member also refuse it. Reading
  reports that last one as the new `unresolved_member` warning.

  Each logical table and derived metric is reported `defined`, `updated` or
  `unchanged`, compared as YAML 1.2, so reformatting is not a change. Nothing is
  deployed: dex runs no `CREATE SEMANTIC VIEW`, no YAML procedure and no grant, and
  opens no Snowflake connection.

  On `transform plan`, a declared mart becomes a logical table:
  - the grain as its primary key;
  - dimensions and time dimensions from its roles;
  - a fact per measure, and a metric per declared aggregation, held non-additive
    over time where the measure is semi-additive;
  - a relationship to each parent table keyed on its foreign key.

  The table is spliced into the file that holds its parents, or proposed as a view
  of its own. A `declarations` payload on `semantic snowflake plan` annotates an
  existing table, rewriting only the lines it changes, comments inside the table
  included. The population is the last sentence of the table's description, which
  the catalog withholds. Units, NULL rules and assumptions are reported as not
  carried.

  ([#1314](https://github.com/exmergo/dex/pull/1314))
- **`maintain` holds Snowflake Semantic Views to the warehouse, and reconciles them
  through `semantic snowflake update`.** Under `semantic.vendor: snowflake`,
  `maintain schema` reports four codes, with no Snowflake object created. Each
  names the view and the element; a column finding also names the column, and a
  dependency finding lists the elements it takes under `data.reasons`:

  - `declared_column_missing`: a dimension, time dimension, fact, metric,
    relationship column, key or `base_table.definition` reads a column its table
    lost.
  - `declared_relation_missing`: a logical table's `base_table` is gone since the
    baseline.
  - `declared_type_conflict`: `SUM`/`AVG` over text, a time dimension over a
    column that is not temporal, or a declared `data_type` in another family.
  - `declared_dependency_dropped`: whatever Dex's reader then refuses, to a
    fixpoint.

  The severities follow what Snowflake does with each conflict, probed on an
  account. It fails every query that sums text. It answers a text time dimension
  with the column's values, so that finding is advised, never cut. It ignores a
  declared `data_type`.

  `maintain reconcile` cuts the removals out of the files as a plan the reader
  validates, with the comments written directly above each removed entry, keeping
  every other byte. A gone `base_table`, a key or `definition` naming a dropped
  column, and a removal that empties the view stay advisory.

  The fingerprint records which key is the primary key and which a uniqueness
  claim (`key_claims`), and each table's primary key as its declaration, so a
  changed primary key is `declaration_changed`. A contradicted key or
  relationship arity is worded as the view's claim and carries `declared_by` and
  `claim`, since Snowflake trusts a declared key without checking it.
  `key_lost_uniqueness` names the claim too, and `join_cardinality_exceeded`
  carries `declared_by` and `claim` for every native vendor.

  ([#1315](https://github.com/exmergo/dex/pull/1315))

### Fixed

- **Metric View query sources with an aggregate or `HAVING` claim no relation.** A `source` query that aggregates its table (for example `SELECT SUM(b) AS a FROM t`), or filters with `HAVING` and no `GROUP BY`, no longer claims that table as its relation, since the view holds fewer rows than the table. A window function keeps the claim, as it keeps the row count. ([#1302](https://github.com/exmergo/dex/pull/1302))
- **`maintain reconcile` no longer refuses a repository whose only layer is a
  native semantic layer without a schema route of its own.** Its findings are
  advisory there, as they already were for vendors with one. A contradicted primary
  key's advice now names a `semantic <vendor> update` route only where dex authors
  that vendor, and says to change the key in its file otherwise. ([#1313](https://github.com/exmergo/dex/pull/1313))
- **`maintain reconcile` advice follows the semantic layer's claim, and no longer
  promises a test edit with no project to put it in.**

  - A lapsed key a semantic layer declares used to get the dbt advice ("change
    the declared grain"). It now names the layer's route to change the key.
  - A Snowflake relationship's arity is no longer advised as a cardinality to
    declare. It is inferred from the referenced table's key.
  - In a repository whose only layer is a semantic one, a lost key no longer
    warns that a `unique` test has nowhere to go.

  ([#1315](https://github.com/exmergo/dex/pull/1315))

### Added

- Make `dex init` a complete project setup command: create a dbt-backed Dex project or local demo, adopt existing dbt, or configure exploration without dbt. Generate managed README and agent instructions, preserve existing content on reruns, verify the connection, and report readiness and recovery steps in one JSON envelope. Terminal users get guided setup and a concise Enterprise handoff. The legacy `dex transform init` scaffolder and repository-level `.dex/` layout remain available. ([#1232](https://github.com/exmergo/dex/pull/1232))
- **`semantic databricks define|update|plan` authors Databricks Metric View files,
  and a declared mart derives one.** Whole Metric View YAML files on
  `semantic.databricks.files` are validated by dex's port of the YAML 1.1 rules,
  stored as a plan and written byte-for-byte by `transform apply`, with no
  workspace connection and nothing deployed. Writing is stricter than reading: an
  unknown key (`rely` included) and `fields` beside `dimensions` refuse a file the
  plan writes, since Databricks refuses the first and drops `fields` for the second.
  Under `semantic.vendor: databricks`, `transform plan` on a declared mart derives a
  Metric View (fields, `date`/`date_time` formats, measures `<column>_<agg>` with
  currency or percentage formats, `many_to_one` joins with `rely.at_most_one_match`
  where the parent declares that key), included as a second plan where its path is
  configured and proposed otherwise; a `declarations` payload on `semantic
  databricks plan` annotates an existing view, splicing only what changes. A Metric
  View has no metadata key, so a population is carried only as the last sentence
  of the view's `comment`, never as a `filter`, and the catalog withholds it. Dex's
  own writers read and write YAML 1.2, so a join's `on:` key stays text.
  `maintain reconcile` now names `semantic databricks update` as the route. ([#1258](https://github.com/exmergo/dex/pull/1258))
- **`maintain` holds Databricks Metric Views to the warehouse, and reconciles them
  through `semantic databricks update`.** Under `semantic.vendor: databricks`,
  `maintain schema` reports `declared_column_missing` (a field, measure, `filter`,
  join condition or query `source` reading a column its table lost),
  `declared_relation_missing` (a view's or a join's `source` gone since the
  baseline), `declared_type_conflict` (a `date`/`date_time` format on a column that
  is not temporal, a numeric format on text, `SUM`/`AVG` over text) and
  `declared_dependency_dropped` (a field, measure, window or nested join that loses
  an input, `MEASURE()` included), each naming the view, the element and the
  column, with no workspace connection. `maintain reconcile` cuts the removals out
  of the view files as a `semantic databricks update` plan the reader validates,
  keeping every other byte; a gone `source`, a `filter` or query source reading a
  dropped column, a removal a `materialization` lists, and one that would empty the
  view stay advisory. A view re-saved in a spec version Dex does not read is
  `semantic_format_changed`, naming the file. A contradicted `rely` key on
  `maintain grain` is now worded as the Metric View's uniqueness claim, not the
  project's grain, and every `declared_grain_not_unique` carries `declared_by` and
  `claim`. ([#1259](https://github.com/exmergo/dex/pull/1259))
- **Ordinary plan and declare drafting carry an unchanged key from tested or declared input keys.** When an input model is not profiled in the cache, drafting now carries through an unchanged single-column or composite key declared (`meta.dex.grain`) or tested (`unique`, `unique_combination_of_columns`) on that input, without requiring a warehouse profile. The drafted grain evidence records its actual source without implying test execution. Aliases preserve key mappings, while transformations or fan-out joins that can destroy uniqueness do not inherit keys without supporting rules. When profiled warehouse data contradicts a stated key, measured evidence takes precedence and retains relevant warnings and verification obligations. ([#1261](https://github.com/exmergo/dex/pull/1261))
- **`semantic.vendor: databricks` reads Databricks Metric View files as the
  semantic layer.** Name the Metric View YAML files in `semantic.databricks.files`
  and `explore semantic list` (with `--metric`, `--for-dimension` and `--search`)

### Added

- **Join coverage is now measured through a filtered CTE over the rows the model actually joins.**
  A join whose side is read through a CTE or subquery that filters used to come back
  `unchecked` with `filtered_cte`, since probing the physical table underneath would count
  rows the model never joins. When every filtering hop reads one relation, its only reducing
  clause is a `WHERE`, and each conjunct is a row-by-row condition over columns and literals
  (comparisons, `IN` over a literal list, `BETWEEN`, `LIKE`, `IS`, boolean logic, `coalesce`,
  casts, `lower`/`upper`/`trim`, as in `where coalesce(_fivetran_active, true)`), the probe now
  reads that side through the same filter. Counts and denominators are the filtered
  population's, and a key that exists only in rows the filter drops is not a match. The
  record carries `effective_input`: per side, the relation, the scopes it was read through and
  the filters applied. Any other reducer (a `GROUP BY`, `DISTINCT`, `LIMIT`, `HAVING`,
  `QUALIFY`, a join beside the filter, a subquery or clock function, a filter on a computed or
  window column such as `rn = 1`) stays `filtered_cte`, now with a reason that names the scope
  and the shape at any depth. `maintain verify` and `transform build --verify` share the
  change, and the extra filters are priced in the same estimate (#1085). ([#1085](https://github.com/exmergo/dex/pull/1085))
- **A feature retirement keeps its checks when Dex cannot finish scanning the project for the flag's readers.**

### Security

- **Concurrent commands no longer revert each other's exploration cache writes.**
  A command that writes the cache (`explore profile`, `explore relationships`,
  `explore map`, and `explore query` or `explore cluster` when they profile an
  object on demand) merged its profiles into the copy it loaded at its start and
  saved that, so a profile another command saved in the meantime was overwritten.
  That included a PII flag a refresh had just raised, which the query firewall then
  read at its old confidence until the next refresh. Only commands running at the
  same time against one `.dex/` were affected; one command at a time never was.

  - Every cache write now re-reads the stored cache under a new store-level cache
    lock, folds its own profiles into it, keeps any stored profile newer than the
    copy it carried, and saves before releasing the lock. No warehouse query runs
    under the lock.
  - The filesystem and SQLite backends hold the lock on `.dex/cache.lock`, apart
    from the spend lock. The in-memory backend holds it across threads.
  - A storage backend you wrote can offer the same lock through the new optional
    `CacheLock` protocol (`cache_lock(timeout=...)`). Without it, dex still re-reads
    the cache before merging, which narrows the window without closing it.

  Reported by [@catincloudlabs](https://github.com/catincloudlabs).

- **Verification checks the temporal contract of a snapshot-backed status history.**
  A snapshot can build while a model over it disagrees about whether the first
  observation is a transition, whether an unrelated edit counts, or whether a
  timestamp is business or capture time. A model can now declare `history`: its
  snapshot, entity and status, and those policies. `maintain verify` and
  `transform build --verify` derive each entity's expected transition count, latest
  transition and first attainment from the snapshot's versions and the declared
  policy, and report disagreements as entity counts (`temporal_*`). Each contract
  gets a `temporal_contracts` record keeping the snapshot's execution, the assertions
  checked, and what stayed unchecked apart. A policy left out, late-arriving data
  whose business and capture order disagree, or a run in which no entity made a
  transition is never reported as clean. Supported today: one dbt snapshot, one status
  column, one output row per entity.
- **Verification measures join coverage and checks a declared parent population.**
  A left join can keep every driving row and match nothing, so a model builds with
  plausible row counts and every joined field NULL. `maintain verify` and
  `transform build --verify` now measure every equality join a model writes, rows
  and distinct keys apart, and record each one under `join_coverage` as
  satisfied, contradicted, not applicable (an empty input, never reported as full
  coverage) or unchecked with a reason code. A join that matches nothing is
  `join_no_match`; a join the declaration requires is judged against the contract
  rather than a default threshold; and a column a join supplies that came back all
  NULL is reported against its declared NULL rule or the cached profile. A model
  can now declare `population.parent`, the entity it holds one row per, and
  verification counts the parents missing from it and the keys the parent does not
  have. The build path runs the join contract for the first time, priced into the
  build's estimate as `(join overlap probes)`.

### Changed

- **`transform plan` reads set operations from their first branch.**
  a model whose outermost query is a `UNION`, `UNION ALL`, `EXCEPT`, or
  `INTERSECT` previously skipped contract comparison because set operations were
  treated as unresolvable. `transform plan` now reads the model's output columns
  from its first branch (or from the union of branches for `UNION ALL BY NAME`).
  declarations pick this up, refusing a declared column absent from a union as
  they do for a direct SELECT list. ([#1042](https://github.com/exmergo/dex/pull/1042))
- **A temporal contract no longer reads as `satisfied` for a model that does not
  descend from its declared snapshot.** Verification walks the manifest's dependencies, free and
  with no connection. A model that does not descend from `history.snapshot` is
  `unchecked` with `reason_code: snapshot_not_ancestor`, naming the snapshot and any
  other snapshot it descends from, and no mismatch is reported against a history it
  never read. A manifest that cannot answer is `lineage_unavailable`.
- **The agent procedure separates what a request settles from an inferred default.**
  The procedure now names `request` or `contract` as an assumption's evidence only
  when that source actually settles the choice: "event rate per account" alone does
  not say whether accounts with no events belong, so a reasonable choice there is
  recorded as `default`, explained in a line, and the work continues. Observed counts
  describe the data and do not establish an intended population or NULL policy. The
  metadata-quality eval gains an attribution score, graded apart from the SQL, over
  four new tasks.
- **`transform build --full-refresh --verify` checks the rows of the incremental
  models it rebuilt.** A rebuilt model holding materially fewer or more rows than its
  driving parent is now reported as `row_loss` or `row_fanout`, as a table is, and
  the parent's row count is priced in the build's one estimate. An incremental
  model this build did not rebuild, one whose `full_refresh: false` made dbt ignore
  the flag, and a microbatch model keep the skip, named in `warnings`. A microbatch
  model is no longer told to run `dbt compile`, which would not have helped.
  `maintain verify` compares no incremental model, as before.
- **`transform plan` checks the column contract through `select *`.** The comparison
  with `schema.yml` was skipped for every model ending in `select * from final`. It now
  follows a star through CTEs, subqueries and joins, then to a referenced model's SQL,
  then to a cached profile, which the warning names. A skipped comparison says what
  stopped it. Existing projects may see new warnings. Two checks that read the same SELECT
  list also see through CTEs: a declaration naming a column absent from `final` is now
  refused, as it already was for a direct SELECT list, and the resolved-key convention
  warning can fire on more models.

### Fixed

- **Deriving an Ossie document at an already configured path produces a plan.**
  When the document did not exist yet, `transform plan` and `transform declare`
  only proposed its contents and incorrectly asked to add the same path to
  `semantic.ossie.files` again. The derived document is now validated with the
  configured layer and stored as a companion plan that `transform apply` can write.
  Unconfigured paths still require explicit adoption. ([#1024](https://github.com/exmergo/dex/pull/1024))
- **A Snowflake estimate no longer recommends `snowflake.suspend_after_command`
  when it is already on.** With the setting on, dex still quotes a project's first
  command that resumes the warehouse the whole `AUTO_SUSPEND` tail, because it
  counts on a suspend only once it has seen one succeed. The note beside the
  estimate now says so, and says that later commands get the resume minimum. The
  advice next to it used to recommend turning the setting on and running
  `GRANT OPERATE` even when both were done. It now names the `dex config set` only
  while the setting is off and the grant only after a suspend was refused for
  lacking it, and dex drops it once a suspend keeps the tail out of the quote. ([#1025](https://github.com/exmergo/dex/pull/1025))
- **dropped schemas are no longer carried forward as out-of-scope.** when a
  schema holding cached relations was dropped from the warehouse or left empty,
  `explore map` treated it as an unobserved namespace and carried its relations
  forward indefinitely, causing recurring `table_dropped` findings after every
  snapshot. observed namespaces are now derived from what the adapter examined,
  so relations in dropped schemas are dropped from the cache while namespaces
  outside a narrowed `--scope` continue to be carried forward untouched. ([#1032](https://github.com/exmergo/dex/pull/1032))
- **A star's EXCLUDE/EXCEPT, REPLACE and RENAME now match columns the way the
  warehouse does.** A qualified modifier (`exclude (a.id)`, `rename (a.id as
  a_id)`) used to be read as its bare column name, so over a join it also hit the
  other table's same-named column: an exclusion dropped a column the warehouse
  keeps, and a rename swallowed it whole. A renamed column now also keeps its
  star's qualifier, so its lineage resolves in a join instead of being reported
  unreadable, and a REPLACE of a renamed column decides what the column produces
  under its new name (Snowflake runs both clauses), rather than the replacement
  being silently dropped. ([#1036](https://github.com/exmergo/dex/pull/1036))
- **equivalent column data type aliases are no longer reported as mismatches.**
  the column contract in `maintain verify` and `transform build --verify`
  previously compared declared and actual types with a raw case-insensitive
  string match, reporting equivalent spellings like bigquery `int64` against
  reported `INTEGER` or duckdb `int` against `INTEGER` as `column_type_mismatch`.
  type comparison now normalizes connector-specific aliases across integer,
  string, float, boolean, and temporal families, treats parameterized types
  compatibly when metadata reflection omits parameters, and falls back to exact
  matching for unnormalizable types. ([#1037](https://github.com/exmergo/dex/pull/1037))
- **The metadata eval now counts Dex commands invoked through a wrapper bound in
  the same command string.** A shell function (`R() { uv ... run.py "$@"; }`) or
  a variable (`R="uv ... run.py"`) wrapping a Dex invocation used to be invisible
  to the command tally; calls through the bound name now count like direct ones,
  while quoted mentions of the bound name (an `echo` inside the wrapper's own
  body) still stay uncounted. ([#1043](https://github.com/exmergo/dex/pull/1043))
- **Trino profiling no longer counts distinct values of nested and sketch columns.**
  Since the exact-count pass began measuring columns with no distinct count,
  `explore profile` and `explore map` on Trino could run `COUNT(DISTINCT)` on columns
  such as `array(varchar)`, `json` or `hyperloglog`, which report only a non-null
  count. Those columns are now skipped, so they keep no distinct count and cannot
  fail the scan for the rest of the table.
- **`transform build --verify` reports the column contract `maintain verify` does.**
  A verified build could return no findings while `maintain verify` reported
  `column_undeclared` on the same models. The build now reports `column_missing`,
  `column_undeclared` and `column_type_mismatch` for the models it built, from
  metadata, with no added statement or estimate. `data.verification.column_contract`
  names the models checked, those declaring no columns, and those not checked with a
  reason, such as a failed model whose older relation is still in place. Findings do
  not change the build's status. `maintain verify` now reports a relation whose
  metadata cannot be read and carries on, instead of stopping.
